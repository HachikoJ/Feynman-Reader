# Day 1-3 作业演进与当前产品对照

## Day 1：问题与 MVP 假设

Day 1 的原始判断是：用户缺的不是更多资料，而是“逼自己输出”和“有人判断是否讲清楚”的机制。MVP 假设包括用户是否愿意开口讲、是否在反馈后产生“原来如此”的感受。

当前产品已经把这条判断实现为文本教学模拟和角色问答；但“开口讲”中的语音输入、以及用户时长与复用数据，仍未完成验证。因此结课材料将它们保留为下一阶段实验，而非当前成果。

## Day 2：全链路设计

Day 2 设想了认证、选书与模式、六阶段分析、费曼实践、成绩诊断和知识内化。当前产品把费曼实践收敛为直接教学输出，不再增加入门、进阶、高级等额外模式。

当前主链路是：

```text
本地激活/试用 -> 选书或上传文档 -> 六阶段学习 -> 教学模拟 -> 3 角色问答 -> 成绩记录与已读状态
```

其中“学习模式”配置和“提醒偏好”有代码基础，但尚未接入用户可完成的主流程；不在当前已实现功能清单中。

## Day 3：Vibe Coding 原型落地

第 3 天完成了产品骨架、六阶段提示词、文档解析、费曼实践、评分机制与浏览器端试用/激活。之后的迭代重点从“功能堆叠”转为“让状态和反馈可信”：

1. 将角色问答固定为 3 题，消除角色数量冲突。
2. 用稳定角色标识匹配多题评分，避免模型返回乱序时错题赋分。
3. 未通过答案与点评直接可见，不让用户误以为系统无响应。
4. 只有三题全部通过才计入综合得分和已读状态。
5. AI 功能在保存 Key 和调用前强制经过隐私同意。

## 结论

项目从“让 AI 逼我讲”的概念，已经变成一条可运行、可留痕、可校验完成状态的学习练习流程。下一步不是盲目增加功能，而是先用用户研究验证：这种追问和评分是否真的让人更愿意输出、能否帮助用户发现理解盲区、是否会带来二次复习。
